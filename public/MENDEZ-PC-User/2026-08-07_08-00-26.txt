  ## Requirements
  
  - New script, e.g. `RegrantCoreRoleToNewCore.s.sol` — grants
    `CORE_ROLE` on `NexaiIndexToken` to the new `NexaiCore` address, then
    revokes it from the old `NexaiCore` address, using the same

    this project (never revoke before confirming the new grant landed)
  
  ```
  NexaiIndexToken: 0x1C87f4647C0B946A28739725A7F67E94967bbd18
  New NexaiCore:   0x7A7a78F5A28830025023EaBC8ad9cddb7c3d579c

  ```
  
  Sequence within the script:
  1. Grant `CORE_ROLE` on `NexaiIndexToken` to the new `NexaiCore`
  2. Verify via `hasRole()` that the grant actually landed
  3. Only then revoke `CORE_ROLE` from the old `NexaiCore` address
  4. Verify via `hasRole()` that the revoke actually landed
  
  - Do NOT touch `NexaiIndexToken`'s own admin role (that's the
    separate, still-pending `MigrateIndexTokenAdminToTimelock.s.sol`

  pragma solidity ^0.8.20;
  
  import {Script, console} from "forge-std/Script.sol";
  import {NexaiIndexToken} from "../src/NexaiIndexToken.sol";
  
  /**
   * @title RegrantCoreRoleToNewCore
   * @dev Step 3 (and, deliberately, ONLY step 3) of the reviewed
   * NEXAI_Redeployment_Sequence.pdf. Moves NexaiIndexToken's CORE_ROLE (mint/burn
   * authority) from the old NexaiCore to the new one deployed in step 1 and configured
   * in step 2. Same grant-verify-revoke-verify ordering as every prior migration script
   * in this repo (MigrateAdminToTimelock.s.sol, MigrateGovContractsToTimelock.s.sol) -
   * never revoke the old holder's role before confirming the new grant actually landed,
   * so mint/burn can never end up held by neither Core mid-migration.
   *
   * Does not touch NexaiIndexToken's own DEFAULT_ADMIN_ROLE - that's the separate,
   * still-pending MigrateIndexTokenAdminToTimelock.s.sol work, unrelated to this step.
   * Does not redeploy or touch the zapper - that's step 4.
   *
   * Addresses (per contracts/README.md's address table / prior sequence steps' output),
   * unchanged by this script - it only ever calls grantRole/revokeRole on
   * NexaiIndexToken:
   *   - NexaiIndexToken: 0x1C87f4647C0B946A28739725A7F67E94967bbd18
   *   - New NexaiCore:   0x7A7a78F5A28830025023EaBC8ad9cddb7c3d579c (step 1's output)
   *   - Old NexaiCore:   0xB324A0B49dD60f5c1e783DCffbF71ABB368B0c19
   * Testnet only.
   */
  contract RegrantCoreRoleToNewCoreScript is Script {
      address constant INDEX_TOKEN = 0x1C87f4647C0B946A28739725A7F67E94967bbd18;
      address constant NEW_CORE = 0x7A7a78F5A28830025023EaBC8ad9cddb7c3d579c;
      address constant OLD_CORE = 0xB324A0B49dD60f5c1e783DCffbF71ABB368B0c19;
  
      function run() external {
          NexaiIndexToken token = NexaiIndexToken(INDEX_TOKEN);
  
          uint256 deployerPrivateKey = vm.envUint("PRIVATE_KEY");
          vm.startBroadcast(deployerPrivateKey);
  
          // --- Step 1: grant CORE_ROLE to the new Core first ---
          token.grantRole(token.CORE_ROLE(), NEW_CORE);
  
          // --- Step 2: verify before touching the old Core's access ---
          require(token.hasRole(token.CORE_ROLE(), NEW_CORE), "New NexaiCore did not receive CORE_ROLE");
          console.log("Verified: new NexaiCore holds CORE_ROLE:", NEW_CORE);
  
          // --- Step 3: only now revoke CORE_ROLE from the old Core ---
          token.revokeRole(token.CORE_ROLE(), OLD_CORE);
  
          // --- Step 4: verify the revoke actually landed ---
          require(!token.hasRole(token.CORE_ROLE(), OLD_CORE), "Old NexaiCore still holds CORE_ROLE");
          console.log("Verified: old NexaiCore no longer holds CORE_ROLE:", OLD_CORE);
  
          console.log("CORE_ROLE migration complete - mint/burn authority now belongs to the new NexaiCore.");
  
          vm.stopBroadcast();
      }
  }
  One thing worth your attention before running this: grantRole/revokeRole on NexaiIndexToken require the caller to hold DEFAULT_ADMIN_ROLE there (the role-admin for CORE_ROLE). Per the doc comment on MigrateAdminToTimelock.s.sol, that role was never migrated off the deployer EOA — so this only works if you run it with the same deployer key that's held DEFAULT_ADMIN_ROLE on the index token all along. If that's changed since, grantRole will revert.
